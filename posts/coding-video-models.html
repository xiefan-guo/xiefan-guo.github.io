Large language models (LLMs), including multimodal vision–language models (VLMs), increasingly serve as the decision-making core of video-production systems: they translate intent into plans, source code or prompts, operate renderers, video generation models and editing tools, inspect intermediate outputs, and revise a deliverable. This survey is motivated by frontier LLMs such as GPT and Claude Opus: run inside coding agents such as Codex CLI and Claude Code, they can now write, render, inspect and revise complete video projects, so that a video increasingly becomes a program the model maintains. We review the agent layer this makes possible, concentrating on configurations in which the LLM writes, executes and revises code or orchestrates generators from code-level plans; earlier LLM-planned video methods are summarized as context.

It classifies each configuration first by task type—code-rendered video, video-model-driven generation, editing and post-production, and video world models in which programs or engines hold state while renderers or video models produce observations—and then by workflow form: direct generation, staged planning and execution, execute–inspect–revise loops, and continuing interaction; cross-task adaptation, in which skills, memory or policies carry over to later tasks, is treated as a separate dimension. The comparison distinguishes the language-model backbone, agent harness, editable artifact, execution tools and feedback, and covers academic methods, agentic evaluations and industrial systems while recording the autonomy and evidence level of each. Film-grade production agents, which turn a brief into a multi-minute film through scripts, references, shot plans, generation, review and assembly, receive dedicated treatment as the most demanding generation setting. We synthesize how planning, executable intermediate representations, critics, memory and computation allocation affect each task, connect methods to their reported benchmarks, and derive a research agenda on reliable delivery, critic independence, preservation under edits, and agreement between executable state and generated pixels.

Keywords: large language models; multimodal agents; video agents; coding agents; video generation; code-to-video; agentic video editing; film production agents; video world models; tool use; evaluation.

Literature and primary-source checks extend through 31 October 2026. This survey defines its task boundaries, terminology, method taxonomy and evaluation contracts within the article.

1. Why frontier LLMs change video generation

Frontier LLMs such as Claude Opus and GPT, especially when run inside coding agents such as Claude Code and Codex CLI, provide a general interface between a natural-language request and an executable video project. Because these agents write and execute code, a video can be treated as a software project—source files, assets, prompts and render scripts that are compiled, inspected and revised—rather than as the output of a single generation call. They can write animation code, plan shots, call video generation models and editing tools, inspect frames, and revise the result. The research opportunity is to turn these capabilities into a reliable process for temporal, audiovisual artifacts. Unlike a single response, a completed video depends on decisions distributed across source files, prompts, generated clips, tools, time and export—and an interactive video world additionally depends on state that must stay consistent with what is rendered.

Recent evaluations make the motivation concrete. VibeVideoBench[1] evaluates GPT-6 Astra in Codex CLI and Claude Opus 5.5 in Claude Code, alongside other native agent systems, on code-driven audiovisual delivery. Code2Video-AA[2] and Code2Video-Compass[3] instead request source in a single call without execution feedback: the former asks for one HTML composition per brief, while the latter spans text-, image- and video-conditioned tasks under a shared rendering stack. These are different kinds of evidence: a complete agent run versus a model's single-call coding capability under two benchmark-defined interfaces. Their results motivate this survey without establishing that a particular model or harness is universally best.

The same agent layer now sits in front of video generation models. A language model may decide the scene, write a program that fixes motion and camera, and select or prompt a diffusion model that supplies appearance; alternatively, the entire video can be rendered conventionally from code. In video world models, an engine or agent-written program may hold persistent state while a video model renders observations. At the far end of generation, industrial systems such as HyCreator[4] now plan, generate, review and assemble films of several minutes from a single brief. We refer to all of these configurations as LLM-driven video agents. The questions of interest are what the LLM controls, how execution and visual evidence affect its next decision, and whether the full process delivers the requested result.

1.1 From LLM planners to coding agents

LLMs entered video generation first as planners. Between 2023 and 2024, DirecT2V[5], Free-Bloom[6], LLM-grounded video diffusion (LVD)[7], Dysen-VDM[8] and VideoDirectorGPT[9] had GPT-class models write frame-level prompt schedules, layouts, scene graphs or multi-scene plans that a diffusion model then realized; MovieFactory[10], Vlogger[11], VideoStudio[12], VideoGen-of-Thought[13], DreamRunner[14], StoryAgent[15], Anim-Director[16], DreamFactory[17], AesopAgent[18], Mora[19] and SPAgent[20] extended such plans to multi-shot stories and tool chains; and GenMAC[21], FlowZero[22], VideoRepair[23] and PhyT2V[24] added critique of layouts, prompts or generated clips. The coding route appeared at the same time in prototype form: GPT4Motion[25] and Kubrick[26] had LLMs write Blender Python, Keyframer[27] generated CSS animation code for SVG illustrations, LogoMotion[28] generated anime.js animation code for layered logos, Data Player[29] scheduled chart animations, LAVE[30], ExpressEdit[31] and Reframe Anything[32] interpreted editing requests through tools, Agent-based video trimming[33] automated footage trimming and story composition, and LLMR[34] edited interactive worlds through generated code. These works established the separation between a language-level plan and its realization that later systems inherit, but their language models mostly emitted plans in one or a few calls; the few that executed and repaired code—Kubrick, LogoMotion and LLMR—did so for a single scene, logo or set of objects rather than maintaining a complete video project.

Frontier LLMs running in coding agents change that interface. The model no longer only describes a video for another model to realize; it writes and maintains the executable artifact—renderer source, engine or simulation scripts, generation pipelines, edit projects or world programs—runs it, inspects the result and edits the source. This survey follows that coding route. Early planners are summarized here and retained in the method atlas; Sections 3–6 concentrate on systems in which an LLM writes, executes or repairs code, or orchestrates generators from a code-level plan, and on the agentic evaluations that test them.

1.2 Scope and inclusion criteria

A core work makes an LLM or VLM responsible for planning, coding, tool selection or feedback-driven revision while generating or editing video, or while constructing and maintaining a video world model—an interactive world whose observations are rendered or generated as video. Domain-specific pipelines and human-assisted systems remain relevant, but their autonomy is recorded. Single-pass models are included as capability baselines. Core denotes the mechanism studied, not its modality or evidence strength. Open models are included alongside frontier proprietary models, and earlier LLM-planning methods are summarized as context (Section 1.1) rather than reviewed individually.

A supporting work supplies a component directly relevant to those agents, such as an animation-coding backbone, a renderer that turns engine or code state into video, an agentic evaluator, or a diagnostic benchmark. Recovering programs from existing video (Video2Code), purely symbolic code world models without a video interface, ordinary game development and data-generation engines are outside this version’s scope. Pure neural world models, proxy-conditioned diffusion without an LLM stage and camera-control modules enter only as components. Video question answering and retrieval are also outside scope unless they participate in producing or revising the artifact.

1.3 Questions and organization

  3. RQ3 — Task extension: What changes when the agent moves from a bounded video to editing existing footage or maintaining an interactive video world?
  4. RQ4 — Evidence: Which experiments isolate these contributions and establish reliable delivery, temporal fidelity or consistent interactive behavior?

2. The LLM-driven video-agent stack

2.1 Backbone, harness, artifact, tools, and evidence

The backbone proposes plans, code, prompts or tool actions. The harness manages context, files, tools, execution, retries and observations. The artifact is what persists: animation source, a shot plan, a prompt, an edit project, a workflow graph or world state. Tools execute those commitments—renderers, video generation models, editors, engines—and feedback informs the next revision. Two systems using the same backbone can therefore differ substantially in what they observe and what they can change.

Four autonomy settings recur alongside the workflow classification. A single-pass coder emits source once. A domain pipeline calls a model at prescribed planning, coding and review stages. A general-purpose agent selects a sequence of tool actions within its available environment. A human-assisted agent receives user decisions during creation or revision. These describe autonomy and orchestration, not mutually exclusive workflow families. A paper’s agent terminology alone does not identify its workflow.

2.3 Execution routes and responsibilities

Execution and representation are additional axes. The first execution route renders source directly: for example, HTML/GSAP, Manim, Blender or a timeline program. The second uses code or structured plans to control video generation models, then edits and composes their outputs. Hybrid code–pixel systems combine both, letting a program fix structure and a generator supply appearance. Code-only rendering and unrestricted generative-tool orchestration therefore require separate resource contracts even when both deliver an MP4.

For a bounded video, a renderer R maps a project P and assets A to frames, V = R(P, A); in hybrid code–pixel generation a learned generator G refines that proxy under a condition c, V = G(R(P, A), c). A video world model additionally defines a possibly stochastic transition st+1 ~ TP(st, at), in which the program P encodes the rules, and a separate observation process ot ~ O(st) realized by a renderer, a video model or both. Writing that transition, choosing the action and depicting the resulting state are different responsibilities. The remainder compares work through five questions: What is editable? What does the LLM decide? What feedback is available? When does adaptation occur? What does evaluation establish?

3. Code-rendered video: animation, explanation and presentation

In this task the agent writes source—SVG, Lottie, HTML/GSAP, Manim, Blender or a chart specification—that a deterministic renderer turns into video. Subtasks are programmatic animation and motion graphics, educational and algorithm explanations, data videos, and document-to-presentation video. Because the renderer is deterministic, most visible defects can be traced to a location in the source, so execution feedback is comparatively easy to localize; omitted content and behavior supplied by the renderer itself are the main exceptions.

3.1 Direct generation (W1)

LottieGPT[35], OmniLottie[36], VAnim[37] and InternSVG[71] learn structured animation representations—tokenized Lottie programs, sparse SVG states or SVG animation tasks—that are decoded and rendered in one pass. Their contribution is a model or representation for producing the artifact; an autonomous inspection-and-repair loop is a separate intervention. The single-call settings of Code2Video-AA[2] and Code2Video-Compass[3] provide matching W1 configurations for general coding models writing HTML or rendering source. Comparing either with a complete coding agent requires accounting for the latter’s tools, observations and additional attempts.

Direct generation is attractive when the output vocabulary is well constrained and the request fits within one generation. Its limitation is that errors discovered only by rendering have no model-mediated correction stage in the evaluated workflow. Visual-coding backbones such as JanusCoder[72] and VisCoder2[73] improve this starting capability, but their results must be re-measured inside a fixed video harness before they are attributed to video-agent behavior.

3.2 Staged planning and execution (W2)

MG-Gen[38] decomposes an image into layers before an LLM writes per-layer animation code; Vector Prism[74] has a VLM plan motion over the rendered graphic, then recovers semantic SVG groups so that the generated animation code can target coherent parts; Manimator[39] separates a scene description from Manim code generation. For data videos, Data Director[75] stages data analysis, scripting and animation planning, and DataMagic[40] composes a single declarative specification of charts, narration and timing. Presentation-video systems PresentAgent[76] (from documents) and PresentAgent-2[77] (from open-ended user queries, with deep research) stage slide, narration and video composition; PresentAgent-2’s Interaction mode answers audience questions grounded in the generated slides and is evaluated per response, rather than maintaining continuing video state. EduVisAgent[78] remains a supporting comparison for instructional planning: its evaluated artifacts are static SVGs and interactive webpages, standardized to screenshots, so EduVisBench is not a video-generation benchmark.

3.3 Execute–inspect–revise (W3)

Frontier coding agents and native harnesses

The most direct instance of this survey’s premise is a frontier model running in a general coding harness. VibeVideoBench[1] gives such agents—among them GPT-6 Astra in Codex CLI and Claude Opus 5.5 in Claude Code—a brief and requires a finished MP4 built entirely with code, with narration, music and sound effects as each task’s audio policy specifies, so that dependency management, file organization, rendering, frame inspection and export all fall within the evaluated run. HyperFrames[79] supplies a deterministic HTML-to-video renderer and agent skills—the composition format that Code2Video-AA[2] also uses in its single-call setting—so that a coding agent can render, inspect and edit seekable HTML animations. SenseNova 6.8 Code2Video[80] pairs an open coding backbone with a recommended Claude Code harness and production skill; its release provides qualitative trajectories and states that systematic benchmarking is absent, so it demonstrates a model–skill–harness interface rather than benchmark superiority. The domain pipelines below fix stages that a general harness leaves to the model, which makes their feedback channels easier to isolate.

Educational and algorithm explanations

Educational systems make the defect–edit relationship comparatively explicit. TheoremExplainAgent[81] retries code generation after execution errors (up to five attempts); Code2Video[41] combines planning, scope-guided coding and visual criticism; VisualEDU[82] combines code and visual feedback for problem-solving videos; PhysicsSolutionAgent[83] checks long Manim explanations with automated quantitative criteria and VLM feedback. TeachMaster[84] and LASEV[85] use debugging, layout or quality gates during production, and DATAREEL[86] extends the comparison to data-story animation through plan and video critics. ManimTrainer[87] compares renderer-in-the-loop inference with weight training across several configurations.

Feedback channels that localize defects

Several methods sharpen the feedback channel itself. MoVer[42] turns motion requirements into executable predicates and returns failed checks to the animation synthesizer. OmniManim / See Before You Code[88] plans sparse keyframe layouts and supplies structured diagnostics. SGA[89] partially executes code to associate geometric conflicts with source lines and feeds them back for targeted LLM edits, acting as a repair plug-in for two host pipelines, TheoremExplainAgent and Code2Video. ALGOGEN[90] has the LLM write a tracker whose verifiable algorithm traces a deterministic renderer compiles under a style template; drafts are self-refined and repaired up to three times from execution and schema errors. These mechanisms differ in how directly they connect a failed property to editable source; incomplete predicates, sparse keyframes and valid trace schemas each leave other errors possible.

Document-to-presentation video

Document-to-video adds source fidelity to production. Preacher[43] uses plan and video reflectors that trigger re-planning or regeneration when a segment fails its checks. Paper2Video / PaperTalker[91] repairs compile errors through LLM rewrites and responds to layout warnings by generating parameter variants and letting a VLM select one; the layout step is warning-triggered search rather than model-authored rewriting. mPresenter[92] critiques and iteratively refines multilingual presentations, and EvoPresent[93] revises slide content and design with feedback from an RL-trained aesthetic critic; narration and the virtual-presenter video are synthesized without critic feedback. Source-based factual checks and audiovisual alignment are separate targets.

Human-steered animation

Human-steered editors such as Decomate[94] and an LLM text-animation editor[95] keep the user in the revision loop for SVG or kinetic-text animation code; LLM2Manim[96] includes expert review, so its human-learning evidence concerns that assisted pipeline. Human involvement is an additional attribute, not a separate workflow family, and content correctness, render success and learner outcomes should not be substituted for one another.

4. Video-model-driven generation: plan, prompt and revise

Here the pixels come from video generation models. Within this task the survey emphasizes configurations in which the LLM writes executable intermediates—Blender, Three.js or engine programs, or code-level generation pipelines—rather than prompt text alone. The agent’s editable commitments are scripts, shot plans, layouts, motion programs, proxies, prompts and the selection of clips. Subtasks are LLM-planned text-to-video, multi-shot narrative and film production, controlled motion and physics, hybrid code–pixel generation, and advertising or personalized video. Because the generator is usually treated as a black box, a defect is typically detected in the output but repaired through the generator’s inputs—prompts, plans, references or seeds—or by regenerating or editing the affected segment.

4.1 Direct generation (W1)

The direct configuration moves a single decision into the language model. PhyPrompt[44] is a trained single-pass prompt rewriter that adds physical detail before text-to-video generation. Such rewriters change what the generator is asked to do without observing what it produced; their gains should be compared with the same rewriter placed inside an inspection loop.

4.2 Staged planning and execution (W2)

W2 systems expose an intermediate plan—a script, layout, scene graph, motion program, proxy or tool graph—but a failed result does not change a later decision in the evaluated configuration.

Executable programs and hybrid code–pixel generation

The coding route makes the plan executable. GPT4Motion[25], an early instance, scripts Blender motion before neural realization; LAMP[97] uses a motion language; GEST-Engine[98] exposes event-graph operations validated by a state backend; and SIMS[99] has an LLM generate long-form keyframe scripts from retrieved short scripts, then executes them through trained character controllers whose dynamics the LLM does not recover. VideoCoCo[45] renders a Blender draft from LLM-written code and conditions a trained editor on it; only execution-error retries are mentioned, so it is treated as W2 (see the hybrid family below). LiVER[100], World narrative model[101] and Fluid-Gen-Zero[102] expose lighting, event or clip-planning decisions at different interfaces; in LiVER, scene and camera agents form a front-end that translates instructions into renderer controls. PhysGen[103] is a component in which a VLM estimates physical parameters for a rigid-body simulator.

Hybrid code–pixel generation combines both execution routes. VideoCoCo[45] and VAKER[46] are staged instances: an LLM-written Blender draft or structured animated-layout representation conditions the generator, and the reported configurations do not return rendered defects to the program. Code Video Model[48] goes further: GPT-6 writes a Three.js program that lays out the scene, animates objects, places the camera and computes dynamics, and refines it through visual review of the renders; the rendered proxy video and a reference image (user-supplied, or restyled from a representative rendered frame by an image model such as GPT-Image-2) then condition a pretrained video model, with early-step conditioning so that the program fixes structure while the generator supplies appearance. Because the review changes the program before realization, its outer loop is classified as W3. Its CodeVideoBench contains 22 cases in eight categories: gaming, product cinematography, architectural cinematics, physics grounding, bullet time, scene editing, robotics simulation and trajectory variation. Such pipelines make motion and camera directly editable in code. Across this family the shared question is whether an explicit plan survives realization: a valid trajectory or event schedule can still be depicted incorrectly, so the plan and the final video should be evaluated on the same events.

Planned multi-shot narrative

Text-level planning remains common for stories. Beyond the early planners of Section 1.1, MovieAgent[104] and MM-StoryAgent[105] add hierarchical shot or cross-media planning, and ViMax[106] scores parallel candidates and keeps the best, which remains fixed best-of-k selection rather than repair.

Recent staged systems specialize the plan for cinematic or domain constraints. ScripterAgent[47] turns dialogue into a cinematic script that a director agent executes scene by scene, and Camera Artist[107] plans cinematic language and camera behavior across shots. CineAGI[108], DramaDirector[109] and VGTeam[110] stage character, shot or slideshow production; AgentMV[111] and MVWeaver[112] plan music videos, with AgentMV allocating a generation budget over a shared state; and OmniDrive[113] (titled DRIVE-CHOREO in its arXiv abstract) has Qwen2.5-VL director, cartographer and auditor agents write a scene script and layout tokens for multi-view driving video. ScripterAgent and DramaDirector train their planners with reinforcement learning (GRPO), and Camera Artist and MVWeaver fine-tune their language models with LoRA; in these reported configurations the training signal does not change a later draft at inference.

Tool and workflow orchestration

Workflow generation is a further W2 form: ComfyGPT[114] generates ComfyUI node graphs, including video workflows, with retrieval-based validation but no execution feedback at inference, and MultiMedia-Agent[115] plans calls over a content-creation tool library; both are optimized during training. SkillPE[116] routes text-to-video prompts through cinematic skills evolved offline, and AgenticGen[117] selects an advertising strategy before drafting, with business feedback used to train reward models. A tool-using plan does not become a repair loop unless its result changes a subsequent proposal.

4.3 Execute–inspect–revise (W3)

Code, engine and camera programs in the loop

When the intermediate is a program, inspection can return a defect to source. Kubrick[26] has director, programmer and reviewer agents revise Blender Python after VLM inspection of renders; FilmFlow[118] composes executable Blender camera plans that a critic checks after rendering; Cutscene Agent[119] operates Unreal Engine through tool calls and refines camera composition and character staging after inspecting rendered frames; PhysAgent[120] closes the loop with targeted program repair of physical control; and MoReGen[121] returns evaluator feedback on motion reasoning to a code-based coder. Code Video Model[48] (Section 4.2) applies visual review to a Three.js program before realization. Camera and motion planners follow the same pattern with structured rather than free-form programs: CamPilot[122] trains its camera-work planner with GRPO and adds an inference-time evaluator–reviser loop that refines the shot description, camera work or prompt until each shot passes quality checks, and MotionAgent[123] converts described object and camera motion into trajectories and camera extrinsics for image-to-video generation, with a rethinking step that corrects them from the generated video. NEWTON[124] trains a planner whose verifier triggers re-planning over keyframe, computation and prompt tools, and PhysPlan[125] has a VLM edit a grounded physical state graph and re-prompts it when deterministic consistency checks reject the edits; the resulting keyframes guide test-time optimization of a frozen image-to-video model, so its loop checks the plan before generation rather than the generated video. VISTA[126] and PreCoG[127] revise prompts or previews, and FantasyHSI[128] corrects planned human trajectories when a critic detects drift.

Prompt and workflow optimization in the loop

A large group of W3 systems treats the video generator as a black box and revises its inputs. SCMAPR[129] verifies semantic coverage and conditionally rewrites complex-scenario prompts; VQQA[130] turns VLM answers to generated visual questions into semantic gradients for prompt optimization; Agentic I2V optimization[131] refines image-to-video prompts from adherence checks before tuning seeds and guidance; and AESR[132] locates erroneous segments in identity-preserving generation and writes repair instructions for an editing model. ComfyMind[133] composes ComfyUI workflows by tree search with localized execution feedback. These loops revise the request rather than the generator, so their gains depend on how faithfully the critic localizes the defect and on the number of generations each revision costs.

Multi-shot narrative and film production

Long-form systems apply the same pattern at shot and story level. Mind-of-Director[134] combines a Discuss–Revise–Judge screenplay loop with engine-level validation of camera parameters against collisions, occlusion and instability; FilmAgent[135] has crew agents critique and revise scripts and camera setups executed in a 3D engine. MAViS[136] refines image and video requests after evaluator checks, FilMaster[137] turns an MLLM audience critique into a revised fine cut, and AniMaker[138], Co-Director[139], A²RD[140] and AutoMV[141] use evaluation-guided search, self-refinement, keyframe iteration or verifier agents. StoryEngine[49] checks intended continuity against rendered evidence, FilmWorld[142] diagnoses and corrects shot-level failures, and VideoGen-Agent[143] uses supervised fine-tuning and reinforcement learning to train tool use across augmentation, generation and verification tools.

Story systems differ mainly in the state they check: GroundShot[144] verifies entities in generated shots and retrieves verified references for later shots, EvoState[145] updates an entity-state memory from observed shots, and MVAgent[146] records how each shot ends to build the next shot’s conditions. CineCrew[50] plans through a film-specification language and refines clips from a critic’s structured checks; MUSE[147] runs a plan–execute–verify–revise loop over identity, composition and continuity controls; OmniAgent[148] lets later nodes in a cyclic crew graph refine earlier outputs; FRAMEWORKERS[149] updates a task stack from execution states and runtime failures; and One Sentence, One Drama[150], Manga2Animate[151], AnimeAgent[152] and SPIRAL[153] use reviewer or critic agents against the script, source panels, attributes or sub-action plans. CHIEF[154] adds the creator: a refiner agent applies the creator’s revisions each round, informed by persona-conditioned MLLM critiques. The comparison should isolate what changes after feedback, rather than count critics or agent roles.

Advertising, personalized and goal-directed video

Advertising and personalized video follow the same pattern with brand or persuasion criteria: Genflow[155] critiques frames against retrieved brand parameters, CogenPVG[156] pairs generators and critics at argument, storyboard, asset and editing stages, and PersonaVlog[157] regenerates keyframes and clips from MLLM feedback and rolls back any regeneration that does not improve their scores. For robot goal videos, VideoAgent (self-improving)[158] refines video plans through self-conditioning consistency, with VLM feedback selecting among plans and environment rollouts used for online fine-tuning and Action Agent[159] selects video models and validates prompts iteratively; both are supporting comparisons because the video serves a downstream policy.

Agentic critics and their reliability

Because these loops depend on a model judge, agentic evaluators are part of the generation stack. VideoArgus[160] generates sample-specific rubrics and evidence plans before tool-assisted scoring of generated or edited videos; Open-EA[161] and Evaluation Agent[162] plan multi-round, few-sample evaluations of generators; and VideoGen-Eval[163] combines structured prompts with tool-assisted MLLM judging. Don’t Read the Log[164] shows a failure mode specific to agent loops: when open-weight VLM judges see an execution trace reporting success, they accept most failed clips, whereas the frontier closed judges tested are largely unaffected. An over-accepting judge ends the repair loop on undetected failures and thereby caps the true pass rate the loop can reach. A critic used inside the loop should therefore be isolated from the agent’s own logs and validated separately from the final evaluation.

4.4 Film-grade production agents

Film-grade production is the most demanding case of video-model-driven generation. A brief must become a story, a script, character, location and prop references, a shot plan, generated clips, sound and an assembled cut, while identity, style and narrative remain consistent across clips that are generated independently. The academic multi-shot systems of Sections 4.2–4.3 study parts of this chain under fixed or disclosed backbones; industrial systems now deploy the complete chain as products. This survey classifies both with the same task → workflow scheme and records autonomy and evidence separately (Table 3).

HyCreator[4] is the most explicit industrial instance. Its developers describe it as an agent harness for long video generation that plans the whole film before generating its parts. A one-sentence brief is expanded, whereas a detailed brief keeps its existing decisions and only the gaps are filled. Key decisions in the story, script and production plan are written as structured artifacts that later stages read; the agent then establishes character, location and prop references, sends a reviewed production plan to the generation model, and assembles accepted clips with picture and sound. Review is layered: textual plans are first checked for narrative and production logic, then reference images, clips and the full film are checked visually for characters, settings and continuity, and only the failing parts are redone; its published trajectories also dispatch a subagent for independent review. The developers state that an end-to-end Auto Mode, offered at Lite and Pro quality, produces films of about ten minutes without human intervention while real-time interactive editing remains available. Under the present classification this is a W3 configuration with an optional human-steering attribute. Its public evidence is a gallery of films with replayable creation processes; no benchmark, ablation or failure rate has been published, so the ten-minute figure is a developer statement rather than an independently measured result.

Other industrial systems occupy different points of the autonomy range. Hailuo Video Agent[165] uses LLM tool invocation across ideation, asset sourcing, storyboarding, editing and voice-over, and describes a roadmap from templates to fully autonomous production. Vidu Agent[166] generates complete short films with storyboards, scripts and music from a simple idea; its product page does not describe review or shot-regeneration controls. Google Flow Agent[167] is a Gemini-based creative partner that plans and reasons with the user’s inputs and under the user’s control; Luma Scenes[168] renders nothing until the user approves a keyframe storyboard and then re-renders only a changed scene; LTX Studio[169] turns an uploaded script into scenes, storyboards and consistent character elements inside a human-operated studio; and Runway Agent[170] selects among several generation models, diagnoses and rebuilds underperforming marketing content that the user shares, and takes edit direction in plain language. Most of these systems keep the human in control—through templates, a storyboard approval gate or conversational direction—rather than closing an automatic review loop, so they are W2 or human-steered W3 configurations, and none publishes the length or failure rate of an unattended run.

Company-lab reports form an intermediate evidence tier. ScripterAgent[47] introduces ScriptBench and a critic for script–video alignment. DramaChain Bench[171] evaluates every stage of a short-drama chain—script, storyboard, keyframes, shots and assembled episodes—with an in-house agent calibrated against commercial short-drama platforms, 5,785 items each scored by three professional annotators, and an agentic judge; its annotations show that upstream defects cascade into final episode quality. That finding states the central evaluation requirement for film-grade agents: each stage should be scored against the original script intent, and coherence should be assessed after assembly rather than only clip by clip. Industrial systems also route requests to proprietary generators that change over time, so demonstrated outputs are not reproducible results; a fair comparison fixes the generators, records human interventions and reports delivery and failure rates over a stated set of briefs.

5. Editing and post-production: change what was asked, keep the rest

Editing starts from existing footage or a project and adds a preservation obligation: the requested change must not erase accepted content. Code-level editing—timeline project files, FFmpeg commands, Blender and simulation programs—is where the coding route is most direct, and the chapter emphasizes it. The agent’s commitments are timelines, edit decisions, tool workflows and effect programs; subtasks include instruction-driven editing, long-form compilation and mashups, music-synchronized cutting, VFX insertion and remaking.

5.1 Direct generation (W1)

Text-to-Edit[51] has a multimodal LLM map raw footage and a request directly to editing decisions for short advertisements, and Timeline Assembler[52] edits a compact timeline representation in one pass from an instruction. Both move editorial decisions into the model; neither reports a render-and-inspect stage.

5.2 Staged planning and execution (W2)

Unified agentic video editing[172] runs open-ended Claude Code planning with evaluation judgments in its trailer setting, a W3 secondary configuration, while previews and summaries use fixed multi-step workflows. AutoVFX[54] writes programs against neural-scene, simulation and Blender modules to insert physically simulated effects. Aurora[53] grounds an underspecified edit through tool calls but plans before generating without a critic; VideoAgent[173] optimizes an editing-pipeline graph against LLM-computed criteria before execution, which is plan-level critique rather than repair of rendered output. L-Storyboard[174] selects and orders shots over language storyboards, and CineAgents[175] compiles instruction-driven cinematic videos from a reverse-engineered narrative memory.

5.3 Execute–inspect–revise (W3)

Agents that edit a persistent project or program can localize repair. Cassette-Editor[58] returns located diagnostics and repair options when an edit to a persistent project is invalid. Crayotter[176] couples diagnostics, intermediate renders and local re-execution, and a follow-up of Crayotter[177] trains a long-horizon editing agent in the Crayotter environment with group-relative preference backpropagation, rendering and revising with tool diagnostics. ELLMPEG[178] generates and locally verifies FFmpeg and VVenC commands with iterative self-reflection; command verification is narrower than perceptual video critique.

Multi-agent editors add perceptual critique. EditDuet[56] explicitly coordinates an editor and critic; GLANCE[57] reconciles local revisions with global music-grounded structure through a verify-and-re-execute loop; CutClaw[179] has a reviewer agent gate, by rejection sampling, the candidate clips that an editor agent selects from hours-long footage within a playwriter’s music-anchored shot plan, sending the editor back to search alternatives. DIRECT[55] cascades screenwriter, director and editor agents for video mashups, and an MLLM validator rejects candidate shot sequences so that the director revises its query; MMLVE-Agent[180] decomposes multi-instruction editing of long videos into shot-level operations and refines corrective prompts when VLM QA agents flag failed edits or unpreserved regions. Auto-Director[181] revises edits through a critic’s reflect-and-revise loop on alignment and pacing, and Soap2Soap[182] audits identity and stability to regenerate selected segments when remaking long episodes. UniVA[183] plans and acts over tool servers for generation, editing and tracking.

The requested change, preservation outside its target and the cost of intervention should be measured separately, because a generator’s quality score cannot capture unnecessary edits.

From bounded videos to worlds. A generated or edited video is finished when it is delivered. A video world model must keep answering new actions: its state and rules persist, and every observation must agree with them. The next chapter separates authoring that world, repairing it against tests, and maintaining it during interaction.

6. Video world models: executable state and rendered observations

A video world model produces observations in response to actions. In the configurations reviewed here, an LLM or coding agent writes or maintains part of that world in executable form—entities, physics, rules or GUI state—while a renderer or video generation model depicts it. Subtasks are code-mediated GUI worlds, engine- or program-controlled generative worlds, physically grounded 4D world construction, and continuing interactive worlds. Purely symbolic code world models share the program-synthesis lineage but lack a video interface and are outside this version’s scope.

6.1 Direct proposals (W1)

Code2World[59] and gWorld[60] predict the next GUI state as renderable web code from the current screen and action, combining linguistic precision with rendered visual fidelity. Each call proposes one next observation; persistence across calls is supplied by the calling agent, so repeated prediction is not by itself a maintained world.

6.2 Staged world construction (W2)

Programmable world model[61] and BoxWorld[62] use agent-authored programs to maintain state and provide visual conditions for a video generator; BoxWorld’s PairedStateBench evaluates fine-grained interaction control with paired state conditions. Their engines can evolve continuously after construction, but the demonstrated authoring configuration should not be labeled an online LLM workflow merely because rendering is interactive. Code world model: Coding agent as world brain[63]—unrelated to the open-weights CWM code LLM of the same name—proposes a continuing agent–code architecture; its reported prototype customizes supplied engine code, records a user-controlled proxy sequence and then generates video offline. This is staged implementation evidence for an ambitious architecture, not an independent demonstration of continuous visual-feedback code revision. AppDeltaWorld[187] retrieves structure before predicting GUI code deltas.

6.3 Execute, inspect and repair (W3)

Physically grounded 4D world construction

World builders repair geometry and behavior against rendered and simulated evidence. Code2Worlds[64] and SimWorlds[188] revise dynamic scene programs; Code2Worlds-2[189] adds physical compilation and simulator feedback. ChronoAgentic[66] combines a description of the rendered rollout with deterministic physics checks before repairing PyChrono programs; Text2Sim[190] uses an independent critic and distilled debug cards for Genesis simulations; WorldAgent[191] verifies geometry, simulation state and rendered views after every construction step; GS-Agent[192] drives a physics engine through code with multimodal feedback; and SimWorld Studio[193] repairs Unreal Engine code from compile errors, physics checks and VLM critiques. ArtiMo[194] targets articulated animation, and Authoring for living worlds[195] has director and scene-builder agents construct executable multi-actor event graphs through tool operations checked against simulator state, which an engine renders into narrative video.

AgentGarten[65] checks multi-view rollouts and contact, collision-clearance and occlusion probes before repairing scene programs; the authoring mechanism is demonstrated qualitatively, while renderer metrics and later agent practice evaluate different stages. A newly authored rule should implement the user’s request, and tests should probe held-out interventions rather than only the trace used for debugging.

Agent loops around generative worlds

CoDeR[196] uses registration and feedback to maintain reusable visual knowledge for code-planned, diffusion-rendered worlds; persistent memory alone does not assign W4. SCOPE[197] optimizes a video world model’s text directives, sampling, verification rules and selection through bounded, evidence-supported edits on development data before freezing the policy for held-out evaluation, an agentic tuning loop around a learned world model rather than code-authored state.

6.4 Continuing interaction (W4)

In W4 the agent consumes fresh interaction evidence while the world runs. Oneira[67] makes action-conditioned decisions over the current world representation and observed frame; Mallea[68] extends behavior and memory during interaction. GameDirector[69] uses a small LLM (Gemma-4-E2B) to select a boss character’s skills at each decision point from estimated spatial context; the engine updates explicit game state and enforces rules, then prompts a video world model that serves as renderer. Matrix-Game 4.0[70] pairs a lightweight rule engine with a multimodal coding agent that turns player requests into edits of scene configurations and game code (designed for use during play; the demonstration customizes game modes in natural language on existing game code), and with a real-time autoregressive renderer that upgrades low-poly engine proxies; the latency of the agent’s edits is not reported. WorldStream[198] compiles hierarchical plans from a typed decision model into a persistent world record, rendered by a WebGL engine, and applies language edits online as the user moves; the paper does not state whether that decision model is a language model, so it is a qualified entry. LLMR[34] provides an earlier human-directed runtime world-editing loop, whose code inspector should not be mistaken for an independent visual judge. Stateful Harness[199] has a coding agent author and freeze typed rules once, after which a VLM proposes per-turn state updates from generated clips that the runtime validates; it is a supporting state-maintenance interface rather than a method that learns or revises rules online. These are different forms of continuing control, not interchangeable implementations of one world-model algorithm.

6.5 Renderer components

Renderers turn coarse or semantic world state into observations and are the pixel half of hybrid code–pixel worlds. AnyGameRenderer[200], Streaming code world model[201], StreamRender-H3[202] and EdenLive[203] expose interfaces from engine or code-world state to video. SolarRenderer[204] targets layout, motion and camera produced by game engines or coding agents; Generative World Renderer[205] and its distilled streaming successor Generative World Renderer at the Speed of Play[206] condition video generation on engine G-buffers; Magpie[207] serves white-box engine frames to a real-time render server; and Coarse-to-Real[208] turns coarse simulation renders into realistic populated scenes. None of these renderers makes an LLM decision itself. StreamRender-H3’s evidence is specific to its racing scenario and engineering profiles, and the streaming code world model is not yet real time. A complete agent claim must also account for the construction and revision of the state being rendered.

What the workflow comparison adds. Direct proposals test representation and model capability; staged pipelines test decomposition; repair loops test the use of feedback; continuing interaction tests the response to new evidence. The same task can use several of these forms. Training, number of agents, memory and human participation qualify the comparison without replacing this hierarchy.

7. Agent mechanisms across tasks

7.1 Feedback that localizes a defect

A critic is useful when it identifies an actionable defect. Compiler feedback diagnoses execution; geometry can locate layout conflicts; temporal predicates can expose an incorrect event order; rendered frames or audio reveal failures not present in source-level checks; probe cameras and engine queries expose behavior beyond a single rollout. The most localizing channels are task-specific: motion predicates and geometric diagnostics for code-rendered video (MoVer[42], SGA[89]), visual questions and entity verification for generated video (VQQA[130], GroundShot[144]), located diagnostics for editing (Cassette-Editor[58]), and engine queries for worlds (AgentGarten[65]). A learned visual critic has broader coverage but requires independent validation; Don’t Read the Log[164] shows that exposing the agent’s execution trace to that critic can inflate acceptance.

7.2 Training, test-time search, and cost

ManimTrainer[87] crosses training strategies (ManimTrainer: supervised fine-tuning and GRPO) with inference strategies (renderer-in-the-loop, with or without API documentation) in nine combinations. Direct animation models and supporting visual-coding components such as JanusCoder[72] and VisCoder2[73] should be distinguished from their inference harnesses; an improved backbone and a better harness are different experimental interventions. Several planners—DramaDirector, MVAgent’s orchestrator and CamPilot’s camera-work planner—are trained with reinforcement learning, which changes the policy but not the per-task loop; CamPilot’s inference-time evaluator–reviser loop is a separate mechanism.

Shorter Is Not Cheaper[209] finds that compact declarative animation specifications, although shorter in answer tokens than free-form code, did not consistently reduce total output including reasoning, latency or failure rates. Cost should therefore be measured as total model output, tool calls, renders, generations and time, alongside delivery, semantic fidelity and later editability.

7.3 Cross-task adaptation

Cross-task adaptation changes what a system brings to later tasks—skills, memory, rules or policies—rather than revising the current artifact (W3) or responding to fresh actions while a world runs (W4). It is the recurring form of improvement in code-rendered video and video-model-driven generation, neither of which has a primary W4 configuration: a finished video is a bounded deliverable, and persistent project files, memory and multi-turn chat do not by themselves introduce a stream of fresh external actions. ManimAgent, Jiang et al.[210] uses frozen cross-task memory rather than weight updates, and Reels-RSI[185] links revisions to fixing diffs and human-approved rules. VideoWeaver[184] composes foundation skills into a workflow for each case and uses an agent-as-judge, which reads both the execution trace and the final video, to evolve reusable skills for later cases; CineForge[186] couples per-story revision with cross-story policy evolution; SkillPE[116] evolves cinematic skills offline, and AgenticGen[117] trains its policies with reward models learned from online business feedback.

These systems are classified by their per-task workflow with an adaptation attribute. This matches the distinction drawn in Video generation meets agent harness[211] between revising an output, updating harness state, updating generator or evaluator parameters, and changing the improvement procedure itself; only the first is W3 repair within a task. The relevant comparisons are held-out transfer, matched retrieval and computation, memory contamination, and the quality of lessons entering the store.

The relationship labels describe the role of an evaluation resource, not a ranking of evidence strength. Each row separately states the input, output, unit and interpretation boundary. The crosswalk distinguishes B (author-introduced benchmark), E (external evaluation), T (author task set), D (data resource), and Q (qualitative evidence). A dataset is not automatically a benchmark, and a plausible method–benchmark pairing is not a published result. Proposed experiments appear in Section 9, outside this reported-evidence crosswalk. Appendix B retains the selected reported relationships, including production and editing agents, with JSON and CSV downloads.

Some easily confused units deserve explicit treatment. Code2Video-Compass contains 2,104 tasks, while its reported 15-model experiment uses a fixed 1,054-task subset; like Code2Video-AA, it requests code in a single call without execution feedback. VideoWeaver's 285 cases include training, test and out-of-domain partitions, and its judge feedback updates skills between cases rather than repairing the current video. MoVer's prompt variants are not independent scene mechanisms. AgenticVBench runs each model on open-source and, where available, vendor-native harnesses and reports harness-dependent spreads in post-production, whereas Code2Video-AA uses a single call without tools or repair; scores from the two protocols are not comparable. These distinctions affect what generalization a score supports.

Comparisons across these resources also require disclosure of information privileges—reference images, source templates, action labels, simulator state and internet access—and reporting quality on delivered outputs separately from full-set reliability. The useful outcome is a profile of delivery, fidelity, functionality, audiovisual quality, edit preservation and cost. A single aggregate may help within a fixed benchmark, but should not join incompatible tasks or erase which stage failed.

9. Synthesis and open research problems

9.1 What the reviewed evidence supports

RQ1: Frontier LLMs make renderers, video generation models, editors and engines accessible through a common decision interface. Direct rendering, video-model orchestration, editing and persistent world control are all relevant, with different editable commitments. RQ2: Progress depends on how planning and feedback convert intent or observations into local changes, not only on the backbone. Training, search and memory act at different timescales.

RQ3: Editing adds a preservation obligation to generation; video world models add unobserved actions, persistent consequences and agreement between state and pixels. Neither is solved merely by generating an attractive clip. RQ4: Existing protocols measure complementary portions of this process. Their most useful contribution is to expose failures and controlled comparisons, rather than support a universal ranking of video agents.

These are proposed studies, not unreported benchmark results or claims that no prior work addresses the topics. Small instrumented environments can isolate mechanisms before scaling appearance, duration and tool diversity. Once those effects are understood, realistic production tasks test whether they survive deadlines, dependency failures, long context and user revisions.

9.3 Completeness within the chosen scope

Completeness here means covering the task types and causal components of an LLM-driven video agent: code-rendered video, video-model-driven generation, editing and video world models; planning and representation; tools and execution; feedback and adaptation; and matched evaluation. Recovering programs from existing video, symbolic code world models, ordinary game development and data engines are deliberately left out of this version, as are video models that operate without an LLM decision stage except where they serve as components.

Workflow labels are analytical assignments rather than an author-declared universal taxonomy; they were re-checked against primary sources, and several were changed (for example, ALGOGEN, Preacher, MAViS, FilMaster and Mind-of-Director to W3; VideoWeaver’s per-case runs to W2). Assignments marked “Qualified” in the atlas identify configurations whose implementation or feedback boundary remains less explicit. The present evidence is uneven. Specialized pipelines often expose clearer intermediate checks, native agents expose broader production capability, and some video-world systems still rely on qualitative demonstrations. Cross-paper superiority claims remain limited by differences in inputs, tools, budgets and judges. The full-title source catalog and scope audit make those boundaries inspectable as the field evolves.

10. Conclusion

Frontier LLMs and the coding agents built on them shift automated video creation from a single generation call toward an iterative process of planning, execution, inspection and revision; industrial film agents already apply that process to multi-minute films, although their claims still await independent measurement. This survey follows that process across code-rendered video, video-model-driven generation, editing and video world models. Their shared research object is the agent that makes and revises decisions through programs, prompts or tools; their different outputs demand different evidence. The next step is to establish which structures and feedback mechanisms turn promising model capability into reliable temporal artifacts, preserved edits and coherent interactive behavior under realistic resource limits.
