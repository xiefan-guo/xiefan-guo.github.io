A chart with exactly four bars, a diagram whose arrows connect the right nodes, and a ball that hits the floor before bouncing all require more than plausible appearance. They require a representation of what exists, how its parts relate, and what changes over time. A program can make those commitments explicit. A visual generator can supply the appearance that would be expensive to author procedurally. The research question is how to connect these two capabilities without losing the commitments in translation.

This post surveys that connection across images, video, editable graphics, 3D scenes, and interactive worlds. My central argument is that the useful unit of study is the contract between execution and visual realization. Writing code is one way to construct the contract; rendering a correct program is only an intermediate success. The final image or video still has to depict what the program specifies.

1. What execution actually guarantees

Let $x$ denote a request, $c$ a program, $e$ its execution environment, $d$ the rendered controls, and $y$ the delivered visual result. A common factorization is

$$ c \sim \pi_\phi(\cdot\mid x),\qquad d=\mathcal{R}(c;e),\qquad y\sim G_\theta(\cdot\mid x,d). $$

The coder chooses a concrete construction; the executor computes its consequences; the realizer translates those consequences into an image or video. The executor can also export object IDs, depth, masks, trajectories, or event logs. Calling all of these a “draft” hides substantial differences in the information the realizer receives.

Suppose $C$ is the set of requirements extracted from the request. It is useful to distinguish three events: $A$, the program encodes the intended requirements; $B$, execution realizes them in the draft; and $D$, the final visual output satisfies them. The probability that all three stages succeed factors as

$$ P(A\cap B\cap D)=P(A)\,P(B\mid A)\,P(D\mid A,B). $$

This is a decomposition of pipeline success, not an empirical model or a claim of independence. Code primarily makes $B$ inspectable. It does not ensure $A$: a script can faithfully execute a mistaken interpretation. Nor does it ensure $D$: an editor can add a fifth bar, alter a label, or shift a collision. A final result might even satisfy the request after correcting a bad draft, so final-task accuracy and faithful execution should be reported separately.

The compiler analogy is useful only with an explicit semantics. A program, its execution trace, and the requested image should agree on named entities and predicates, such as “four bars,” “the label is 12,” or “contact precedes rebound.” A stochastic image editor is an additional transformation whose preservation of those predicates must be measured. Calling code an intermediate representation does not give that transformation the guarantees of a semantics-preserving compiler. Likewise, “code as CoT” describes an operational intermediate; an executable trace alone does not establish a faithful explanation of the model’s internal reasoning.

Precision is conditional on a representation

A renderer can place four rectangles at specified coordinates. Whether the viewer sees four distinct bars also depends on clipping, occlusion, camera projection, and legibility. A simulator computes the dynamics of its chosen model, numerical solver, and parameters; it does not establish that the inferred materials or forces match the intended physical situation. A browser can typeset an exact string, but missing fonts and overflowing containers can still make it unreadable.

Reproducibility is similarly conditional. Record seeds, assets, fonts, renderer and library versions, solver settings, and execution limits. With a fixed environment, code offers a much stronger basis for replay than a natural-language plan. Arbitrary Python, GPU simulation, or a browser loading changing remote assets is not automatically deterministic.

Finally, the optimization barrier is more specific than “rendering is non-differentiable.” diffvg differentiates rasterized images with respect to continuous vector parameters. The harder discontinuities are often in program tokens, topology, object creation, branching, and tool calls. Continuous parameter fitting and discrete program search can therefore be complementary.

2. The lineages and the roles of code

The foundations include program induction, learned drawing policies, and procedural modeling. Ellis et al. inferred programs with loops and shared structure from hand drawings; CSGNet recovered constructive-solid-geometry programs and learned without program annotations through policy gradients; SPIRAL trained a drawing agent through an external graphics engine using adversarial rewards. ShapeAssembly encoded hierarchical part attachments in a domain-specific language. These works already studied executable structure and learning through rendering, before modern language-model orchestration.

The vocabulary itself can be learned. DreamCoder alternates program search, abstraction discovery, and recognition-model training; ShapeCoder discovers reusable functions and parametric relationships from collections of shape primitives. Their relevance is not unrestricted photorealistic generation. It is the possibility of learning a representation whose editable degrees of freedom match recurring structure, instead of always generating a long sequence of low-level coordinates.

The modern layout-to-image branch adds a learned appearance generator. VPGen decomposed generation into objects/counts, layouts, and images; LayoutGPT used stylesheet-like visual plans; LLM-grounded Diffusion used captioned boxes; and RPG planned regional generation. These works establish the value of explicit structure, although a layout specification is a narrower intermediate than a general scene program.

Control-GPT already executed GPT-4-written TikZ sketches and used them to condition diffusion in 2023. GPT4Motion used generated Blender scripts and simulated scene components for video. REVISION supplied rendered 3D spatial guidance. In parallel, SceneCraft developed code–render–inspect refinement for Blender scenes, while The Scene Language combined hierarchical programs, semantic words, and identity embeddings with traditional, neural, or hybrid renderers. These are related lineages, rather than evidence that every later system directly descends from one predecessor.

Its preprint reports experiments but explicitly lists no public code or checkpoints in its reproducibility checklist; it should not be treated as equivalent evidence for an executable system.

3. Images: drafts or layered composition?

CoCo: a useful result with a specific domain

CoCo uses a BAGEL-based unified model to write drawing code and refine its executed draft. CoCo-10K supplies text–code pairs and text–draft–final triplets; training combines code supervision with image-generation supervision. It demonstrates large gains on structured and text-intensive images.

A particularly relevant comparison is DraCo, which previews, verifies, and refines a low-resolution pixel draft. It gives a non-code alternative to intermediate visual reasoning. However, different datasets, objectives, and inference procedures prevent a cross-paper comparison from being a controlled ablation of representation alone. The same caution applies to comparisons with textual reasoning in GoT and T2I-R1.

Routing among renderers

GenClaw illustrates the agentic route: construct context, write a task-appropriate sketch through code, and use an image model to enrich it. SVG, HTML/CSS, plotting, Canvas, or 3D tools offer different control vocabularies. Such a system can change tools without retraining the whole generator, but tool selection, execution failures, and repeated generation become part of the inference cost.

The important distinction is where adaptation occurs. A unified model can learn the two stages together; an orchestrated pipeline can optimize or replace them separately. Neither architecture is inherently cheaper or uniquely capable of training the coder against final-output rewards. A black-box realizer can still supply sampled rewards for policy optimization if the coder is trainable.

Keep precise elements in the final compositor

There is another architecture: generate the difficult visual assets, then assemble the final design under code control. Editable visual design uses visual references and generated assets alongside native HTML/CSS, with rendered feedback for refinement. Its evidence is primarily case studies and showcases. The useful design choice is that text and layout remain editable components of the delivered artifact.

PosterVerse uses HTML-based scalable typography in a poster workflow. TransAnyText generates renderable HTML patches for translated image text, combines them with diffusion-based background processing, and uses deterministic rendering for final synthesis. The order matters: having a generator repaint a text layer introduces a different failure surface from compositing that text after background generation.

My practical rule is to assign a precise requirement to the latest stage that can enforce it. For a poster with a date, price, and product photograph, the photograph can be generated while the strings and their placement remain browser-rendered. A full-frame neural rewrite may still be appropriate when letters must interact with scene geometry or lighting, but it should earn its extra flexibility through final-output checks.

4. Video: specifying and checking a process

For a sequence, a program specifies more than a frame layout. It can represent initial conditions, contact, forces, event order, and camera motion. The central distinction is between animating a desired trajectory and simulating a causal mechanism. A keyframed bounce may satisfy a director’s request without validating the physical explanation of that bounce.

VideoCoCo: draft construction and editor adaptation both matter

VideoCoCo constructs a low-fidelity Blender simulation, generates an appearance-focused editing instruction, and adapts a video editor using VideoCoCo-3K draft–instruction–target triplets. The paper reports PhyGenBench improving from 0.475 to 0.558 and VBench-2.0 from 52.18 to 77.88.

Verify the simulated event before paying for realization

PhysAgent treats physical programs as executable hypotheses. It separates scene state from event control, checks reconstruction and diagnostic simulation in stages, and repairs failed factors through semantic action APIs. Its ablation reports PhysReal of 0.631 without reflection versus 0.714 for the full system; removing semantic APIs increases average refinement rounds from 3.63 to 5.74. This is evidence for structured repair within that benchmark, not proof that a verifier is infallible.

The distinction between outcome and mechanism remains essential. If the prompt says “the ball lands in the bucket,” a position constraint can verify the outcome. If it says “after rolling down the ramp,” the event trace must also check support, release, contact, and ordering. A visually plausible ending can conceal the wrong process.

For explanations and motion graphics, direct code rendering is often sufficient. TheoremExplainAgent, Code2Video, and ManimTrainer / ManimAgent study executable animation workflows. MoVer verifies spatial and temporal predicates of SVG animation; LottieGPT models vector animation tokens; VAnim models sparse updates to a persistent SVG DOM. Their editability and verification techniques are relevant even when the target application ultimately needs neural appearance.

5. Worlds: persistent state and faithful observations

One-shot generation ends with an artifact. An interactive world must keep evolving after the camera turns away. Action-conditioned video models such as Matrix-Game and Hunyuan-GameCraft provide a useful adjacent baseline: explicit executable state is an architectural alternative to retaining world information through visual history.

In a program-driven world, let $s_t$ be persistent state, $a_t$ an action, $v_t$ the camera, and $m_t$ appearance memory. A useful abstraction is

$$ s_{t+1}=T_c(s_t,a_t),\qquad d_{t+1}=P(s_{t+1},v_{t+1}), $$

$$ y_{t+1}\sim G_\theta(\cdot\mid d_{t+1},y_{\leq t},m_t). $$

The transition function owns world evolution; the proxy exposes some of that state; the renderer produces an observation. This separation lets us ask three different questions: did state evolve correctly, did the proxy expose the relevant consequence, and did the rendered video show it?

From an architectural proposal to interaction and memory

Code World Model combines a coding agent, persistent executable state, and proxy-conditioned MiniMax-H3 rendering. Its proxies encode geometry and semantic information. The paper’s results are qualitative, and its limitations explicitly include small training scale, the absence of autoregressive real-time generation, and difficulty constructing complex mechanisms from scratch. It demonstrates a promising decomposition rather than a quantitatively established replacement for a game engine.

A lighter bridge is to turn game state into instructions for the generator, as explored by GameDirector and RIGen. Text can convey event semantics but does not itself localize every entity. An important adjacent counterexample is MASS: it separates an authoritative typed state from view rendering while learning the transition engine, without hand-written transition functions. Explicit state, executable rules, and code generation are separate choices.

Two memories and one authority problem

Remembering “the door is open” is different from remembering the door’s scratches and paint. The first belongs to semantic state; the second needs appearance binding or memory. Returning to an object after an occlusion tests both. In a multiplayer setting, each camera must observe consequences of the same authoritative state, even though some consequences are temporarily invisible.

There is also a less discussed boundary: generated observations can introduce objects or details absent from state. If an agent promotes such an object into the executable world, it needs an identity, geometry, affordances, and consistency checks. Otherwise the renderer can silently expand the action space, or two views can disagree about what exists. I would treat this as a controlled state-commit operation, not an automatic consequence of plausible rendering.

The naming has older meanings too. WorldCoder, GIF-MCTS, and Code world models for general game playing synthesize executable dynamics for planning. Meta’s CWM is a code language model trained with execution-related experience. Neither label alone implies a proxy-to-video renderer.

6. Inverse graphics and editing: source should remain useful

Generation from text and reconstruction from an image have different ambiguities. An image can be reproduced by a meaningful scene program, a pile of view-specific polygons, or a single textured plane. Similarity in one view does not establish usable geometry or semantics. A good program representation should support a requested intervention after reconstruction.

More formally, two programs can be observationally equivalent under the training camera while responding differently to an edit or a new viewpoint. Reconstruction therefore identifies an equivalence class, not necessarily the original source. Evaluate a recovered program on withheld cameras, parameter changes, and object-level edits; where observations cannot determine hidden structure, retain alternatives or report uncertainty. Exact source matching would incorrectly reject many valid constructions, while pixel matching alone would accept a view-specific shortcut.

For vectors, StarVector models SVG code with semantic primitives, while OmniSVG uses discrete command and coordinate tokens. Chat2SVG combines LLM-generated templates with diffusion-guided path optimization, providing a hybrid of semantic construction and continuous refinement. These methods help distinguish a useful vector description from a visually similar but unwieldy tracing.

In 3D, VIGA interleaves code, rendering, and inspection. Thinking in Blender stages refinement of geometry, materials, composition, and lighting. Recursive Code World Models gives unresolved scene parts their own reconstruction loops and then revisits the whole. That global–local–global structure addresses a practical problem: a detailed local solution can still be wrong in camera alignment or relation to its neighbors.

Assets need similar structure. CAD-Recode reconstructs sketch-extrude CAD sequences as Python from point clouds; MeshCoder reconstructs Blender programs from point clouds; LL3M and Nova3D generate programmable Blender assets. Named parts, constraints, and articulation are useful interfaces for a future world simulator. Merely retaining a source file does not prove that those interfaces are correct.

StepCAD makes construction state part of inference: its policy observes target and intermediate geometry, while geometry-guided tree search revises CAD programs. This is a useful alternative to predicting a complete program once. Its reconstruction metrics establish geometric performance under the tested search budget; they do not by themselves establish preservation of future design intent.

HistCAD supplies a complementary test. In its October 2026 revision, predictors receive existing construction histories with sketch constraints removed and predict constraints without seeing the later edit request. Success requires matching the initial geometry, reaching the edited dimension, preserving specified relations and unedited dimensions, and rebuilding the complete history. In one reported Industrial setting, 34.2% of assigned tasks reach the target and rebuild, but only 29.0% also preserve the required relations. This is evidence for measuring usable editability separately from executability. The task supplies geometry and feature history; it should not be described as unconstrained image-to-CAD synthesis. [HistCAD, Table 2]

Editing makes this distinction measurable. EdiTikZ learns from revision-derived scientific figure edits rather than only synthesized edit instructions. ChartEditBench evaluates sustained multi-turn chart modification; VisEditBench tests feedback-guided repair and reference-guided restyling. Each asks more than “can the model produce a similar picture?”: it must change the requested content while retaining the rest.

The GUI branch exposes a related question about reachable next states. Code2World and gWorld predict screens through renderable code; AppDeltaWorld predicts transition-grounded code updates. A screenshot can look right while representing an impossible action outcome. Evaluation therefore needs transition validity as well as visual fidelity.

7. Learning from execution

Supervised code is a starting point

There are many valid programs for the same image. Token-level imitation can penalize an alternative correct construction while overlooking a small numerical change that radically alters a render. Useful data must align requests, source, rendered outputs, and execution context. AutomaTikZ and DeTikZify develop TikZ data and synthesis; VisCoder / VisCode-200K includes validated plotting and correction experience. SciTikZer adds execution-centric scientific graphics data and round-trip verification in its dual self-consistency RL framework.

Generated code can also supply visual supervision. Factuality Matters constructs 1.3 million structured image pairs from executable programs and introduces StructBench. Infinigen provides a broader procedural-generation precedent. Programs can produce labels and controlled variations that would be costly to annotate manually, but renderer and template diversity remain limits on the distribution learned.

Three different sources of reward

For a runnable candidate, a useful conceptual reward decomposition is

$$ r=\alpha r_{\mathrm{spec}}+\beta r_{\mathrm{visual}}+\gamma r_{\mathrm{edit}}-\lambda\,\mathrm{cost}. $$

This is a design sketch, not a single objective shared by the cited methods. Specification rewards check values, connectivity, bounds, or event traces; visual rewards check similarity and perceptual quality; edit rewards check the requested change and preservation. Execution failures should be handled explicitly rather than silently excluded. Aesthetic preference cannot substitute for a failed hard requirement.

The weighted sum above is appropriate only for criteria whose trade-offs are acceptable. For exact labels or required connectivity, use feasibility-first selection: reject candidates that fail a validated hard check, then rank the survivors by appearance and cost. If no candidate passes, report failure or repair it. During training, soft penalties may provide useful gradients or policy signals, but finite penalties do not turn a learned system into a hard-constraint solver. With uncertain visual checks, report calibrated error rates and audit the selected outputs rather than treating a passing judge as proof. The reward-model survey develops this distinction between predicting criteria and choosing an aggregation rule.

  • Outcome rewards. RLRF learns from rendered SVG feedback; VinciCoder uses coarse-to-fine visual RL across code domains; TikZilla combines improved TikZ data with RL; and UI2CodeN studies interactive visual optimization.
  • Geometric and structural rewards. GeoSVG-RL constructs a layout plan and uses browser-backed checks for canvas fit, anchors, text containment, and graph consistency. CTRL-S combines structured SVG generation with multiple visual, format, and efficiency rewards. These make different aspects of correctness explicit rather than compressing them into one similarity score.
  • Learned and rubric rewards. Visual-ERM models fine-grained rendered equivalence. RULER derives instance-specific rubrics for open-ended SVG instructions. These can cover requirements without a reference image, but they inherit judge uncertainty and reward-hacking risks. ChartJudgeBench directly evaluates visual judges in chart reproduction and editing.

From one terminal score to localized visual feedback

Execution feedback can change the model’s observation, the search procedure, or the training reward. These are distinct interventions. Diffusion on syntax trees for program synthesis edits grammar-conforming syntax trees and combines its proposal model with execution-guided search. Preserving syntax reduces one class of failures, while rendered feedback still determines whether the program meets the visual specification.

Render-in-the-Loop instead feeds the cumulative rendered canvas back into the model before it generates the next SVG primitive. Its ablation finds that simply prompting unadapted models with intermediate renders gives no consistent gain; it trains on such visual-code trajectories. This observation feedback differs from assigning rewards to intermediate renders. The paper reports a 1.50× latency increase over its open-loop SFT baseline, mostly from decoding, and its accepted drawing actions are additive: the model cannot delete or replace earlier primitives. Seeing an error and having an action that repairs it are separate capabilities. [Ablations, cost, and limitations]

Reinforcement learning from intermediate renders uses executable program prefixes to localize learning signals. At valid drawing boundaries, a closure operator makes a prefix renderable. Changes in visual score provide progress rewards, propagated back to tokens and combined with final-outcome supervision. In compact notation,

$$ d_j=\mathcal{R}(\mathrm{close}(c_{\leq b_j})),\qquad \Delta_j=S(d_j,x)-S(d_{j-1},x). $$

Not every arbitrary code prefix is executable; the boundary and closure rules are part of the method. Nor does every correct construction improve similarity monotonically: a background layer can temporarily cover an object before a later command restores it. The paper combines process and outcome signals rather than relying on intermediate progress alone. [Method and prefix closure]

RefineSVG attacks a different feedback problem: an initial SVG is rendered, a multidimensional visual residual is returned, and the model performs a correction. Its progressive training includes supervised learning and agentic RL. The broader lesson is that learning to repair a diagnosed mistake is different from learning to emit a successful first attempt.

Self-improvement needs an external check

RSI closes a cross-capability loop: diagnose generated images, write programs targeting weaknesses, verify rendered examples, and train generation, understanding, and program writing. On BasicChartBench L0, the paper reports 45.7% to 60.2% after four rounds, versus 46.3% for continued training. Its human audit also finds that readers still accept roughly a third of requirements judged absent from native generations. Verified construction improves the supervision source; it does not remove every downstream perceptual error. [Tables 1–2]

The remaining training question should be stated narrowly. Execution-feedback RL already exists, and an external renderer is compatible with policy gradients. What is less established by this literature is joint optimization of program construction and a separate stochastic visual realizer, evaluated on final constraint survival at practical cost. A reward on the draft alone can prefer a precise but difficult-to-realize proxy; a reward on appearance alone can prefer a beautiful violation.

8. What a convincing evaluation needs

Make constraint survival measurable

For each observable requirement–sample pair $i$, let $b_i$ indicate satisfaction in the executed draft and $f_i$ satisfaction in the final output, using explicit, aligned tests. My proposed diagnostics are the survival rate $\widehat S$ and the repair rate $\widehat R$:

$$ \widehat S=\frac{\sum_i b_i f_i}{\sum_i b_i},\qquad \widehat R=\frac{\sum_i(1-b_i)f_i}{\sum_i(1-b_i)}. $$

Report the denominators and mark an empty stratum as undefined. These rates distinguish preserving a correct draft from correcting a wrong one, but neither replaces final accuracy or the fraction of prompts satisfying all requirements. A high survival rate on easy drafts can conceal poor construction. Compare realizers on the same draft pool, stratify by constraint type and difficulty, and cluster uncertainty estimates by prompt. Hidden state should be checked against execution logs; it should enter a visual score only when an observation makes it identifiable.

For example, an assertion that a chart contains four bar objects checks source state. A rendered-image test must also check that four distinguishable bars are visible and their labels remain readable. To test actual use of the controls, change only one bar value or swap two event times while keeping a prompt compatible with both variants fixed, then check the corresponding output change. This counterfactual control test distinguishes fidelity to the supplied program from success caused by the generator’s prior.

Check the delivered observation against the program

PROWBench directly tests the missing interface. It contains 170 programmatically constructed episodes and 600 proxy videos, with state and timestamped event records. Evaluation includes entity control, Logic-Render Alignment, Interaction Success Rate, long-horizon reappearance, and multiple views. In its 30-second setting, reported bounding-box IoU is only 0.175–0.280 and reappearance IoU 0.053–0.131. Its authors caution that state scores have few events, use an uncalibrated judge, and compare different window-chaining protocols. The evidence supports a significant fidelity problem, not a universal model ranking. [§4.4]

For editing, Pixels or Code? introduces VAO-Bench with 1,573 tasks across nine artifact categories. Its main protocol gives all systems the source image and instruction; code-based systems do not receive original source code. The paper evaluates direct edits, dependent updates, preservation, validity, and visual quality. Explicit dependency instructions help more than source access in its diagnostic experiments. That is evidence that a source representation alone does not solve the reasoning needed to edit it. [Protocol and diagnostic experiments]

Evaluation can itself use explicit structure. TIFA decomposes faithfulness into visual questions; Davidsonian Scene Graph organizes questions with dependencies to reduce inconsistent judgments. EPIC uses a fixed predicate program to verify images and route failures to editing or resampling. Such checks are powerful, but an exact predicate evaluated by an uncertain detector is still an uncertain visual measurement.

How far can coding agents go in visual generation? studies code-only drawing on AgentDrawBench’s 200 prompts and finds a profile of structural strength and limited perceptual richness. SGP-Bench tests semantic understanding of graphics programs without seeing the render. Together they motivate measuring the coder, the renderer, and the complete system separately.

A minimum experimental protocol

The following is my proposed protocol, rather than an existing benchmark standard:

  1. Separate errors by stage. Measure execution success, draft constraint satisfaction, final satisfaction, and the survival of constraints already satisfied in the draft. Log cases where the realizer fixes a draft as well as cases where it breaks one.
  2. Match the actual budget. Compare direct generation, text plans, pixel drafts, code-only rendering, code-conditioned generation, and layered composition with matched wall time or tool/compute budget. Include retries, asset retrieval, compilation, and critic calls.
  3. Test interventions. Change one requested value or rule, then measure requested changes, necessary dependent changes, and preservation elsewhere. For worlds, test occlusion, revisits, counterfactual actions, and synchronized cameras.
  4. Count every attempt. Report timeouts and failed renders in the denominator, plus completed-only scores for diagnosis. Provide seeds, environment versions, sample counts, confidence intervals, and human calibration of automatic judges.
  5. Use held-out constructions. Split by templates, scene families, and program structure where possible. Include portraits, textures, and other tasks with little expected code advantage to measure routing overhead and quality regressions.

9. Research directions with testable hypotheses

The most useful next step is to turn architectural intuitions into falsifiable comparisons. These are six experiments I would prioritize.

Constraint-aware routing

Hypothesis: the best pipeline depends on which requirements need exact enforcement, not simply on whether the prompt is an “image” or a “chart.” Compare a fixed code-first pipeline with a router choosing direct generation, a spatial proxy, or layered composition. Supervise route choice with measured quality–cost trade-offs. The experiment fails to support routing if its decision overhead or misclassification erases the gain. Include unfamiliar task mixtures, not only the categories used to design the router.

Learn reusable visual abstractions

Hypothesis: a learned library of typed construction and edit operations improves transfer beyond low-level coordinate prediction. Compare a fixed DSL, a learned library, and general-purpose scripts on held-out combinations and subsequent edits. Count library definitions as part of representation complexity, keep asset access and search budgets comparable, and test whether an operation preserves its intended relations under parameter changes. Compression without successful new constructions or edits would not support the hypothesis.

An interface that exposes identities and events

Hypothesis: object IDs, geometry, and event markers preserve different constraints better than RGB drafts alone. Export several synchronized representations from the same executable worlds and train comparable adapters. Measure count and identity binding, event timing, and appearance quality at matched bandwidth and compute. Ablate each channel. This would distinguish better information in the controls from a better-trained generator.

Final-output verification with localized repair

Hypothesis: repairing the failing stage is more efficient than resampling the whole chain. Save the program, draft checks, and final-output checks. A wrong trajectory triggers a program edit; a correct trajectory rendered incorrectly triggers realization repair; a corrupted label triggers deterministic recomposition where the output format permits it. Compare success per unit cost against unconditional retries, using a held-out judge and manual audits to detect verifier exploitation.

Joint optimization with a separate constraint score

Hypothesis: learning programs for their eventual realization improves final satisfaction beyond optimizing draft quality alone. Begin with a fixed realizer and optimize a trainable coder with sampled final rewards, then alternate updates. Track draft correctness, final correctness, appearance, program complexity, and cost separately. Test multiple realizer seeds and a held-out realizer so the coder cannot win solely by exploiting one generator’s quirks. This can use policy gradients without differentiating through arbitrary program execution.

Explicit commits from pixels back into world state

Hypothesis: explicit entity registration and state-compatible appearance memory improve long-horizon interaction. Construct episodes where an object is discovered, acted on, occluded, and revisited by a second camera. Compare fixed executable state, unverified observation-to-state updates, and verified commits with stable IDs. Ablate texture memory separately from semantic state. Score impossible interactions and conflicting observations, not just the visual similarity of returning objects.

Across these experiments, I would preserve a simple division of responsibility: executable representations make commitments inspectable; the visual model makes them visible. Progress means improving the measured agreement between the two while retaining the appearance, flexibility, and cost needed by the application.

10. Reading paths and reference index

For the foundations, read graphics-program induction → ShapeAssembly → ShapeCoder: they progress from recovering structure to choosing operations and learning reusable abstractions. Compare Render-in-the-Loop with intermediate-render rewards to distinguish feedback as an observation from feedback as supervision; use HistCAD to make editability an operational test.

For the core idea, read Control-GPT → CoCo → Editable visual design: the sequence contrasts a draft with a structured final deliverable. For motion, read GPT4Motion → VideoCoCo → PhysAgent. For interactive worlds, read Code World Model alongside PROWBench, then examine Oneira, AgentGarten, and Mallea for different extensions.

For learning, start with RLRF, then compare GeoSVG-RL, Intermediate renders, and RSI: they change the verification signal, the granularity of credit, and the source of training data, respectively.
